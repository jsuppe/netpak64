SC64 fork — wire interconnect (dual uplink)

Block-level signal map for a NetPak64 adapter forked from SummerCart64: the existing cart-bus front end is inherited unmodified; a new register block, an SPI bridge, and one ESP32 network module — built-in Wi-Fi plus an optional wired uplink via W5500 — are added.

Fidelity note: this is a block/interconnect diagram, not a pin-accurate schematic — SC64's real KiCad pinout was not available while drafting it. Signal groups and their direction are accurate to the design docs and the simulated gateware; exact FPGA/MCU pin numbers are not shown and must come from SC64's actual board files at build time.

01Signal path

Left → right: console, through the unmodified cart bus, into the FPGA (existing SC64 logic plus one new register block), across the fork boundary, to a single new network module with two uplinks — built-in Wi-Fi, and an optional wired path via W5500 — both terminating at the same relay. Dashed horizontal rail below carries power and ground.

04Confirmed vs. open

✓ Confirmed

  • Clock/reset port names (clk/reset) match SC64's real n64_dd.sv.
  • SC64's reg bus is byte-addressed — n64_netpak.sv defaults correctly.
  • n64_netpak.sv probe logic simulates green on Verilator (both addressing modes proven).
  • RTL ↔ netpak-core differential conformance: 96,425 lockstep checks, 0 mismatches.
  • DD's irq pattern is the template for the new block's cart-IRQ line.
  • ESP-IDF officially supports W5500 as an SPI Ethernet MAC/PHY (esp_eth component, Espressif's own docs) — one MCU genuinely covers both uplinks.

⚠ Still open

  • Exact FPGA/MCU pin assignments — needs SC64's real KiCad project.
  • Power budget: does the existing 3.3V regulator have headroom for ESP32 (incl. Wi-Fi TX bursts) plus an optional W5500, populated together? Bigger unknown now than a single-uplink design.
  • Dom2 bus timing on real silicon (H1) — the #1 unretired hardware risk.
  • Where SPI physically breaks out on a shipping SC64 board (free GPIO vs. a board revision) — now needs two SPI buses, not one.
  • Uplink-selection firmware policy (prefer wired-if-linked, else Wi-Fi) — a config default, not an open architectural question.
  • DTLS transport (separate design doc) would terminate in the ESP32 shown here — not yet wired into this diagram.
