NetPak64: Emulator as a Network Endpoint

The game sees a NIC, not netplay.

NetPak64 adds a spec-defined, memory-mapped network device to the ares Nintendo 64 emulator, making each instance a first-class network endpoint. Homebrew games link against a libdragon driver library and implement their own netcode — state sync, lockstep, or prediction — just as they would on real hardware.

What is NetPak64?

NetPak64 is a complete networking solution for Nintendo 64 homebrew that bridges emulator and hardware through a shared register-level hardware specification:

📋 Spec-First Design

A versioned device contract on the PI bus, not an emulator API. The same ROM binary later runs unmodified on a physical adapter, enabling emulator ↔ emulator play now and emulator ↔ console play once hardware follows the spec.

🎮 Homebrew-Focused

Designed for the N64 homebrew community using libdragon. Developers run two ares instances plus a local relay on one machine for fast iteration. No flashcarts, USB bridges, or PC-side tether required.

🚀 Device-Level Networking

Games see a network device, not synchronized inputs. They implement their own netcode (the proven approach for custom ROM development). The library provides datagram send/recv, session management, RTT/clock, and both unreliable and reliable channels.

💡 Self-Hostable Relay

A single static Rust binary using tokio, speaking an efficient UDP protocol. Rooms with join codes, star-topology forwarding, presence events, and shared clock. A $5 VPS serves a community.

Key Design Decisions

Spec-as-Contract, Not API

The register-level device specification on the N64's PI bus is the durable contract. Emulator implementations, firmware, and future ports all satisfy the same spec. This is what makes the same ROM binary playable across different backends — a property we want to preserve.

Three Architectural Constraints

  1. Zero behavioral diff when disabled. With NetPak off, ares is bit-identical to upstream. Keeps the fork mechanically rebasable and an upstream RFC credible.
  2. Emulation-thread state ownership. All device state the CPU can read is owned by one thread. The net thread touches only lock-free queues and an atomic. Savestates are race-free by construction; loopback runs are deterministic.
  3. Thin, reusable glue. The in-ares diff stays ≤ ~500 lines. All real logic lives in `netpak-core` so it can be reused for firmware and other emulators without dragging the whole ares fork.

Device-Level, Not Input-Lockstep

Unlike gopher64 or simple64 netplay (which synchronize controller streams), NetPak64 gives the game a real network device. Games implement their own netcode — state sync, snapshot interpolation, or lockstep prediction — matching their design.

Hardware-Plausible Spec

Every choice stays implementable by an MCU/CPLD: trivial decode at a fixed address, software-programmed timing registers, single-packet TX, exposed-head RX. The spec carries VERSION/CAPS negotiation from day one so a hardware revision doesn't strand ROMs.

Key Differentiators

vs. gopher64/simple64: Input-lockstep netplay is perfect for retail games. NetPak64 gives homebrew a real device and lets it choose its own netcode model (state sync, prediction, lockstep).
vs. N64-NetLib: Closest prior art. NetLib validates demand but requires a flashcart + PC bridge + Java servers. NetPak64 makes the emulator itself the endpoint, with a relay as the only external service (self-hostable on a $5 VPS).
Future hardware: The spec is emulator-first but hardware-plausible. When the adapter project is ready, a physical implementation follows the same spec, and ROMs don't change.

Trust Model (v1)

Plaintext UDP with two secrets: a per-connection random 32-bit token (frame authenticity + identity across NAT rebinds) and unguessable 6-char room codes. Right-sized for "friends playing homebrew." Hardening path (v2): DTLS or Noise-based encryption.
